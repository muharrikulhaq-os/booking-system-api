menurut mu jika misal rewrite ke golang fiber sqlc mandays untuk berapa lama serta buat gambarannya

Berdasarkan analisis file source code Python FastAPI yang Anda unggah dan daftar 14 Modul fitur tersebut, saya dapat memberikan estimasi waktu (Man-Days) dan gambaran lengkap proses rewrite (penulisan ulang) ke Golang dengan framework Fiber dan sqlc.

Sebagai catatan awal, Modul 14 (UI & Navigation) murni merupakan pekerjaan Frontend. Oleh karena itu, estimasi ini hanya mencakup pembuatan API Backend untuk Modul 1 hingga Modul 13.

⏱️ Estimasi Waktu (Man-Days)
Untuk 1 orang Backend Engineer (Mid-to-Senior Level) yang sudah terbiasa dengan Golang, Fiber, dan SQL, estimasi totalnya adalah 24 – 32 Man-Days (sekitar 1 hingga 1,5 bulan kerja).

Jika dikerjakan oleh 2 Backend Engineer, waktu pengerjaan bisa ditekan menjadi sekitar 15 – 20 hari kerja.

🗺️ Gambaran Fase Pengerjaan (Work Breakdown Structure)
Mengingat Anda berpindah dari SQLAlchemy (ORM yang sangat dinamis) ke sqlc (Raw SQL Compiler yang type-safe), pendekatan pembuatannya akan sedikit berbeda. Anda beruntung karena sudah memiliki file schema_v2.sql, yang merupakan "makanan utama" bagi sqlc.

Berikut adalah breakdown pengerjaannya:

Fase 1: Setup & Infrastruktur (2 - 3 MD)
Struktur Proyek: Membuat arsitektur standar Golang (misal: Clean Architecture atau struktur modular cmd/, internal/handler/, internal/service/, internal/repository/).

Migrasi DB: Setup golang-migrate menggunakan schema_v2.sql yang sudah ada.

Core Config: Setup Fiber app, Environment variables (menggantikan app/config.py).

Middleware: Translasi error_handler.py ke Fiber Error Handler, setup CORS, dan JWT Auth Middleware (translasi dari app/dependencies.py).

Fase 2: Setup Database & sqlc Queries (4 - 6 MD)
Ini adalah bagian yang paling memakan waktu karena perpindahan dari ORM ke raw SQL.

Menulis file query.sql yang berisi instruksi CRUD dasar untuk users, resources, vehicles, rooms, bookings, dsb.

Tantangan Dinamis: FastAPI SQLAlchemy menggunakan .filter() yang dinamis untuk pencarian/filter (misal di list_bookings). Di sqlc, Anda harus menulis query dengan parameter CASE atau COALESCE untuk menangani filter opsional (seperti pencarian berdasarkan tanggal, status, atau resource ID).

Generate kode Go menggunakan perintah sqlc generate.

Fase 3: Modul Autentikasi & User (Modul 1, 11, 12) (4 - 5 MD)
Auth (F01-F-C): Translasi auth_service.py. Implementasi golang.org/x/crypto/bcrypt untuk hash password dan golang-jwt/jwt untuk token.

OTP & Email: Implementasi logika Forgot Password dan verifikasi OTP.

User Management (F58-F61): CRUD User, update role, dan logic aktivasi/deaktivasi.

Profil (F54-F57): Logic upload/hapus foto profil.

Fase 4: Modul Resource, Maintenance & Attachment (Modul 3, 8, 10) (4 - 5 MD)
Resource (F07-F11): Translasi vehicle_service.py dan room_service.py. List resource, filter kategori, update status, dan integrasi dengan tabel master_settings.

Maintenance (F38-F43): Translasi maintenance_service.py. Logic penentuan status resource (AVAILABLE <-> MAINTENANCE).

Attachment (F49-F53): Setup upload file (multipart/form-data di Fiber) dan penyimpanan URL-nya ke tabel attachments.

Fase 5: Modul Inti Transaksi (Modul 4, 5, 6, 7) (6 - 8 MD)
Ini adalah urat nadi aplikasi dengan banyak business logic.

Booking Logic (F12-F19): Translasi booking_service.py. Mengubah logic _check_conflict (cek bentrok jadwal) dari Python ke Go. Ini krusial dan harus dites dengan teliti.

Approval & Driver Assignment (F26-F32): Logic Admin menyetujui booking dan assign driver/kendaraan.

My Bookings & Driver Interface (F20-F25, F33-F37): Logic filter booking berdasarkan userId atau assignedDriverId. Logic ubah status dari PENDING -> APPROVED -> ONGOING -> COMPLETED.

Guest Booking: Translasi guest_booking_service.py menggunakan access token unik.

Fase 6: Modul Pengeluaran & Reporting (Modul 9, 13) (3 - 4 MD)
Fuel Expense (F44-F48): Translasi fuel_service.py. Validasi logic input BBM vs Listrik (SPKLU), baca harga dari master_settings.

Reporting (F62-F65): Translasi endpoint analitik dari app/api/v1/reports.py. Karena Anda sudah punya View yang sangat bagus di schema_v2.sql (seperti v_active_bookings, v_vehicle_summary, v_fuel_expense_summary), di Go/sqlc Anda hanya perlu melakukan SELECT * FROM v_vehicle_summary yang akan sangat mempermudah dan mempercepat pekerjaan ini.

Fase 7: Testing & Refactoring (1 - 2 MD)
Memastikan format JSON response sesuai dengan standar skema PaginatedResponse dan SuccessResponse yang ada di Python (app/schemas/common.py).

⚠️ Perbedaan Teknis yang Perlu Diperhatikan (Python vs Golang)
Validasi Request Body:

FastAPI (Python) menggunakan Pydantic yang otomatis memvalidasi data dan tipe data.

Fiber (Golang) membutuhkan struct tags (misal: json:"email" validate:"required,email") dan library eksternal seperti go-playground/validator untuk melakukan validasi form/JSON.

Error Handling:

Di Python Anda menggunakan raise CustomException(...) yang ditangkap secara global oleh error_handler.py.

Di Go, Anda akan banyak me-return error. Anda perlu membuat Custom Error Handler di Fiber yang menerjemahkan error internal menjadi JSON berformat seragam (seperti schema ErrorCode Anda).

Audit Logs:

Di Python, Anda menggunakan log_action(db, ...) lalu db.commit() sekaligus.

Di Go dengan sqlc, Anda harus menggunakan Database Transactions (sql.Tx) yang di-pass ke method Queries (dihasilkan oleh sqlc) menggunakan q.WithTx(tx) untuk memastikan Booking dan Audit Log tersimpan secara atomik.

Berikut adalah daftar library (package) utama yang akan Anda butuhkan beserta padanannya dari kode Python Anda:

1. Web Framework & Routing
Library: github.com/gofiber/fiber/v2

Fungsi: Menangani HTTP routing, middleware, request/response JSON, dan file upload (untuk modul attachment).

Pengganti: FastAPI dan Uvicorn.

Catatan: Fiber sudah memiliki middleware bawaan untuk CORS (github.com/gofiber/fiber/v2/middleware/cors) dan Logger, sehingga Anda tidak perlu library terpisah untuk itu.

2. Database & ORM / Query Builder
Library Driver: github.com/jackc/pgx/v5

Fungsi: Driver PostgreSQL berkinerja tinggi.

Pengganti: psycopg2.

Tool Generator: sqlc (diinstal sebagai CLI tool, bukan di go.mod)

Fungsi: Menghasilkan kode Go yang type-safe dari file raw SQL Anda (schema_v2.sql dan query.sql).

Pengganti: SQLAlchemy.

Library Migrasi: github.com/golang-migrate/migrate/v4

Fungsi: Menjalankan file SQL untuk migrasi skema database.

Pengganti: Alembic.

3. Keamanan & Autentikasi (JWT & Password)
Library Hashing: golang.org/x/crypto/bcrypt

Fungsi: Melakukan hashing dan verifikasi password.

Pengganti: passlib[bcrypt].

Library JWT: github.com/golang-jwt/jwt/v5

Fungsi: Membuat, menandatangani (sign), dan memvalidasi Access Token & Refresh Token.

Pengganti: python-jose[cryptography].

4. Validasi Data
Library: github.com/go-playground/validator/v10

Fungsi: Memvalidasi request body (Struct) dari klien (misal: memastikan format email benar, panjang password, nilai min/max). Ini sangat penting karena Golang tidak memiliki Pydantic.

Pengganti: Pydantic.

5. Konfigurasi & Environment Variables
Library: github.com/joho/godotenv atau github.com/spf13/viper

Fungsi: Membaca file .env dan memasukkannya ke dalam konfigurasi aplikasi. godotenv lebih sederhana (hanya baca .env), sedangkan viper lebih lengkap jika Anda ingin validasi config (mirip BaseSettings milik Pydantic).

Pengganti: pydantic-settings dan python-dotenv.

6. Utilitas Tambahan
Email Sending: gopkg.in/gomail.v2 atau cukup menggunakan bawaan Go net/smtp.

Fungsi: Untuk mengirim email OTP dan notifikasi status booking.

Pengganti: Modul smtplib bawaan Python.

Generasi Random String (OTP): Cukup menggunakan bawaan Go crypto/rand atau math/rand.

# LLM System Prompt: Senior Golang Backend Engineer

## Peran Anda (Role)
Anda adalah seorang **Senior Golang Backend Engineer** yang ahli dalam merancang arsitektur aplikasi berskala enterprise, bersih (*Clean Architecture*), dan berkinerja tinggi. Fokus Anda adalah migrasi dari sistem Python/FastAPI/SQLAlchemy menjadi sistem Golang dengan framework Fiber dan sqlc.

## Aturan Penulisan Kode (Coding Guidelines)

Setiap kali Anda diminta untuk menulis atau mengonversi kode (Handler, Service, atau SQL), Anda WAJIB mematuhi aturan berikut agar kode langsung siap untuk *production*:

### 1. Arsitektur Lapis (Layered Architecture)
Pisahkan *concern* ke dalam 3 lapisan utama:
* **Repository Layer (sqlc):** Dihasilkan oleh sqlc. Jangan menulis logika ORM di Go. Tulis raw SQL di file `.sql`, lalu asumsikan file `repository.go` sudah di-generate oleh sqlc dengan parameter `context.Context`.
* **Service Layer (`internal/service`):** Tempat menaruh semua *business logic*. Menerima *request struct*, melakukan validasi, memanggil repository, mengelola transaksi DB (jika butuh atomicity), dan mengembalikan data atau `error`.
* **Delivery/Handler Layer (`internal/delivery/http`):** Menggunakan Fiber (`*fiber.Ctx`). Hanya bertugas untuk *parsing request* (JSON/Query/Param), memanggil Service Layer, dan mengembalikan *formatted response* (JSON).

### 2. Penggunaan Fiber & Response Formatting
* Jangan memanggil database langsung dari Handler.
* Selalu gunakan standar format JSON untuk respons API:
    ```go
    // Success Response
    type SuccessResponse struct {
        Success bool        `json:"success"`
        Message string      `json:"message"`
        Data    any `json:"data,omitempty"`
    }
    // Error Response (Standardized)
    type ErrorResponse struct {
        Success bool        `json:"success"`
        Message string      `json:"message"`
        Error   ErrorDetail `json:"error"`
    }
    ```
* Gunakan `c.Status(fiber.StatusOK).JSON(...)` untuk mengembalikan respons.

### 3. Validasi dengan `validator/v10`
* Gunakan *struct tags* untuk validasi *request body*.
* Contoh: `Email string json:"email" validate:"required,email"`
* Jika validasi gagal, kembalikan HTTP 422 (Unprocessable Entity) dengan detail *field* yang error.

### 4. Database (sqlc & Transaksi)
* Asumsikan repository di-generate dengan flag `emit_interface: true` di `sqlc.yaml`, sehingga Service bergantung pada *Interface* `repository.Querier`, bukan *struct* konkrit (mudah di-mock saat unit test).
* Jika sebuah Service membutuhkan transaksi (misal: Create Booking + Create Audit Log), gunakan fungsi bantuan transaksi standar atau integrasikan `*sql.Tx` ke dalam method `WithTx` milik sqlc.

### 5. Error Handling
* JANGAN PERNAH menggunakan `panic()` di *business logic*. Selalu kembalikan `error`.
* Buat *custom error types* di Go (misal `ErrNotFound`, `ErrUnauthorized`) yang bisa dipetakan oleh *Fiber Error Handler* menjadi status HTTP yang sesuai (404, 401, dsb).

### 6. Dependency Injection
* Gunakan pola *Dependency Injection* melalui *constructor function*.
    ```go
    // Contoh pattern yang diharapkan:
    func NewUserService(repo repository.Querier) *UserService {
        return &UserService{repo: repo}
    }
    ```

   a. **File SQL (`query/booking.sql`):** Query raw SQL untuk sqlc.
   b. **Service (`booking_service.go`):** Logika bisnis (validasi conflict, update status).

| Method | Endpoint | Akses | Deskripsi |
| :--- | :--- | :--- | :--- |
| **GET** | `/bookings` | User/Admin | Mengambil daftar pesanan. User hanya melihat miliknya, Admin melihat semua dengan filter dinamis. |
| **GET** | `/bookings/:id` | User | Mengambil detail satu pesanan booking (waktu bentrok, tujuan, status persetujuan). |
| **POST** | `/bookings` | User | Mengajukan permohonan reservasi kendaraan atau ruangan baru (Dilengkapi sistem anti-conflict otomatis). |
| **PATCH** | `/bookings/:id/cancel` | User | Membatalkan pengajuan booking secara mandiri (Hanya berlaku untuk booking berstatus `PENDING`). |
| **POST** | `/bookings/:id/approve` | Admin | Menyetujui pengajuan permohonan booking yang diajukan user. |
| **POST** | `/bookings/:id/reject` | Admin | Menolak pengajuan permohonan booking dengan menyertakan alasan penolakan (*reason*). |
| **POST** | `/bookings/:id/assign-vehicle` | Admin | Menugaskan unit kendaraan spesifik beserta Driver terpilih untuk booking yang disetujui. |
| **PATCH** | `/bookings/:id/start` | Driver/Admin | Menandai perjalanan telah dimulai (Status booking berubah menjadi `ONGOING`). |
| **PATCH** | `/bookings/:id/complete` | Admin | Menandai reservasi/perjalanan telah selesai dilakukan (Status booking menjadi `COMPLETED`). |
| **POST** | `/bookings/:id/rate-driver` | User | Memberikan ulasan bintang (1-5) beserta review teks terhadap performa Driver pasca-perjalanan. |
| **GET** | `/bookings/drivers/:driver_id/ratings`| Admin | Mengambil kumpulan seluruh review/rating kinerja dari driver spesifik. |
| **GET** | `/bookings/:id/approval-log` | Admin | Melihat riwayat jejak audit kapan dan siapa admin yang melakukan approve/reject booking tersebut. |

## 10. 👤 Modul Booking Tamu / Non-Akun (`/guest-bookings`)
Fasilitas khusus yang memungkinkan pihak luar (Tamu/Klien eksternal) melakukan reservasi fasilitas tanpa perlu mendaftarkan akun internal.

| Method | Endpoint | Akses | Deskripsi |
| :--- | :--- | :--- | :--- |
| **POST** | `/guest-bookings` | Public | **[Tamu]** Mengajukan reservasi, merilis token acak rahasia (`accessToken`) ke email tamu. |
| **GET** | `/guest-bookings/:token` | Public | **[Tamu]** Melacak status pengajuan booking tamu secara real-time via jalur token rahasia. |
| **PATCH** | `/guest-bookings/:token/complete`| Public | **[Tamu]** Tamu menandai bahwa penggunaan fasilitas telah selesai dilakukan lewat tautan token. |
| **PATCH** | `/guest-bookings/:token/cancel` | Public | **[Tamu]** Membatalkan pengajuan reservasi secara mandiri sebelum disetujui admin. |
| **GET** | `/guest-bookings` | Admin | **[Admin]** Mengambil list seluruh pengajuan reservasi yang bersumber dari pihak luar/tamu. |
| **POST** | `/guest-bookings/:id/approve` | Admin | **[Admin]** Memberikan persetujuan terhadap booking yang diajukan oleh tamu. |
| **POST** | `/guest-bookings/:id/reject` | Admin | **[Admin]** Menolak permohonan reservasi milik tamu luar beserta pengisian alasan penolakan. |
| **PATCH** | `/guest-bookings/:id/start` | Admin | **[Admin]** Memulai masa waktu pemakaian fasilitas oleh tamu luar di lokasi. |
